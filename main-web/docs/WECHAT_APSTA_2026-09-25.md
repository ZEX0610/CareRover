# CareRover 入座/离座推送：AP + STA 接入与现场验收

## 拓扑与现状

- 主板继续提供 `CareRover-xxxx` 热点、`192.168.4.1` 网页和 WebSocket；CAM 仍以 `192.168.4.2` 接入该热点；网页手机或 iPad 也继续连该热点。
- 主板额外以 STA 接入独立的 **2.4 GHz** 手机热点，只有 Server酱 HTTPS 通知走外网。热点手机不必、也不应替换网页设备。不要把主板切换成纯 STA 模式或在发完消息后关闭 Wi-Fi。
- ESP32-S3 的 AP/STA 共用一套射频。外部热点若不在信道 1，主板 AP 会跟随 STA 信道切换；连接瞬间可能让 CAM/网页短暂重连，且视频与上网共享空口带宽。逻辑地址不变不等于零卡顿，必须做现场 A/B。
- 外部热点不得分配 `192.168.4.x` 网段，否则与小车 AP 冲突；程序会跳过推送并报告 `uplink_subnet_collision`。

## 实现边界

- `firmware/main_wireless/seat_notification_gate.h` 只在 IDLE、传感器有效时观察现有 HC-SR04 `seated` 状态；冷启动/重新进入 IDLE 先建立基线，不把旧状态误报为新事件。连续 800 ms 状态变化才出事件；5 s 内第二条被抑制。入座底层阈值仍是 `<30 cm` 连续 3 次，未修改前方障碍策略。
- `firmware/main_wireless/serverchan_notify.cpp` 使用长度为 1 的最新事件队列与低优先级任务；超声波、控制和网页线程都不执行 DNS/TLS/HTTP。断网时当前事件最多保留 60 s；每个事件最多尝试一次 HTTP 发送，避免请求已被服务器接收但响应丢失时自动重试造成重复微信消息。网络失败不改变运动模式。
- 采用 `https://sctapi.ftqq.com/{SendKey}.send`，校验 ISRG Root X1 根证书、设备时间、HTTP 200 与 JSON `code=0`。不打印密钥、热点密码、请求 URL 或响应正文。公用 CA 可随服务器证书链变化而需要更新，现场若仅出现 TLS 失败，应先检查时间和证书链。
- 私有 `wifi_secrets.h` 在本机，不应提交；`wifi_secrets.example.h` 只有占位符。编译检查包也是占位符，**不得烧录 compile-only 包**。

## 现场顺序（尚未执行）

1. 保持舵机 5 V 断开、四轮架空、网页 IDLE；先确认 CAM/网页/手势/人物框/摇杆静态遥测的现有基线，电脑网络保持不变。
2. 确认私有 STA SSID/密码对应当前独立热点、热点为 2.4 GHz，尽量用信道 1；只读检查主板 COM 口、当前版本、备份可回退固件。
3. 仅烧录主板应用；不碰 CAM、NVS、FFat 和已有网页。查看 115200 串口 `ap_ready`、`wechat_push` 状态、主板固件版本；确认 iPad/网页仍能连 `192.168.4.1` 且 CAM 视频恢复。
4. 在 IDLE 用 HC-SR04 实际做“空座 → 入座 ≥ 0.8 s → 离座 ≥ 0.8 s”；确认事件只发一次、手机微信收到消息，并记录 HTTP 状态。若热点/Server酱不可用，验证网页和操控链路仍正常。避免短时间多次触发消耗 Server酱额度。
5. 记录 APSTA 前后视频 FPS、AI 帧率、页面连接稳定度与延迟。若切信道造成明显断流，先把外部热点固定在信道 1；若设备不支持固定，则应考虑独立联网网关转发消息，而不是牺牲现有 AP 的稳定性。
